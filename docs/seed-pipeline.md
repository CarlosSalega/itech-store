# Catalog seed pipeline

Status: **in force**. This is the specification of how a catalogue row of an outside source
becomes a product this store owns in its database, and of which of its photographs survive the
next run.

It was written for `odd/tasks/catalog-layout.md` T0 (spec S6) because these rules lived only as
comments inside four modules, and task T2 deletes every prose comment in
`src/features/catalog/`. The rules are not new: each one was already decided, implemented and
tested. The [Provenance](#provenance) table maps every rule below back to the line that
documented it, so deleting a comment removes the sentence and nothing else.

Three consequences are the reason the rules are written down: a wrong family files a product on the
wrong wall, a wrong selection either sells a model twice or loses it silently, and a rewrite that
ignores what is already written deletes the owner's photographs while reporting success.

## Shape of the pipeline

| Extract | Environment variable | Seed file it writes | Photography folder |
| --- | --- | --- | --- |
| `scripts/extract-catalog.ts` | `CATALOG_SOURCE_URL` | `prisma/seed/products.json` | `/products/<family>` |
| `scripts/extract-iphone-catalog.ts` | `IPHONE_SOURCE_URL` | `prisma/seed/products-iphone.json` | `/products/iphone` |
| `scripts/extract-apple-catalogue.ts` | `APPLE_SOURCE_URL` | `prisma/seed/products-apple.json` | `/products/<family>` |

The seed (`prisma/seed.ts`) reads the three files, keeps the image references that resolve on
this machine, decides the featured products and upserts products and variants. The catalog UI
renders `/placeholder.webp` for a product left with no reference.

## 1. The extracts

**R1 — One source per extract, address from the environment.** Each extract reads its base
address from the environment variable named above. The address is never printed, stored or
defaulted: the repository must carry no reference to the source site. The Apple and phone
extracts never load a `.env` file on their own (they import no `dotenv`, on purpose); the base
extract does (`import "dotenv/config"`). Every error the Apple and phone extracts log has URLs —
and, for the phone source, the anonymous key — replaced before printing.

**R2 — Nothing about price, stock or provenance is extracted.** The seed files carry names,
families, slugs, descriptions, references and variants. Prices and stock are sample data
generated by the seed, and where a row came from is not something this repository records. The
output of a run is product names, families, slugs and counts.

**R3 — Every extract runs dry first.** `--dry-run` writes no seed file and downloads no
photograph; `--limit=N` caps how many records are processed. A dry run reports what it would
have written and stops.

## 2. The Apple classifier

**R4 — A name is in scope only when it carries an Apple word.** The classifier first normalises
the name, then requires an Apple brand or product word (`apple`, `iphone`, `ipad`, `macbook`,
`imac`, `mac mini`, `mac`, `watch`, `airpods`, `pencil`, `airtag`, `homepod`, `studio display`,
`apple tv`). Anything else is not an Apple product and yields no family, whatever its
vocabulary says: a generic `cargador` does not become an accessory because "cargador" is an
accessory word.

**R5 — Accessory vocabulary wins over a device family.** Accessory words (`pencil`, `keyboard`,
`teclado`, `adaptador`, `cargador`, `cable`, `airtag`, `homepod`, `studio display`, `apple tv`,
`soporte`, `beats`, `funda`, `protector`, `templado`, `pantalla`) are checked *before* the
families, because a name can carry both: "Apple Magic Keyboard iPad White" is an accessory, not
an iPad, and a phone case or a screen protector that names its phone is an accessory, not a
phone.

**R6 — Families are tried in a fixed order, and their words do not overlap.** `IPHONE`
(`iphone`), `WATCH` (`watch`), `AIRPODS` (`airpods`), `IPAD` (`ipad`), `MAC` (`macbook`, `imac`,
`mac mini`, `mac`). The first pattern that matches wins. The words were chosen not to overlap,
so no name can match two families and depend on the order.

**R7 — An Apple product with no recognisable family stays out.** Guessing a wall is how a
product lands on the wrong one by the letter of a pattern. A name that passes the Apple gate but
matches no family and no accessory word is dropped rather than filed.

**R8 — Comparison is by words, not by characters.** Every comparison in the module uses the
normalised form: Unicode NFD, diacritics stripped, lowercased, every run of non-alphanumeric
characters replaced by one space, trimmed. Words are the unit, so `USB-C` and `USB C` are the
same product, and so are `–` and `-`.

**R9 — A brand word typed twice is one brand.** A source may list "Apple Apple Watch SE 3
40mm", the brand typed on top of an already branded name. A leading run of repeated `apple` is
collapsed to a single `apple`, so the two spellings compare equal and the store names the
product once.

**R10 — This module knows nothing about the source.** It is pure and does no fetching: names go
in, names and families come out, so every decision above can be tested without a network.

## 3. The requested list

**R11 — The list is the whole policy.** `REQUESTED_APPLE_PRODUCTS` holds the Apple products to
import, by Apple product name, reviewed and chosen by the owner:

```
iPhone 18 Pro - 256 GB
iPhone 18 Pro Max
iPhone Duo 256 - 512 GB
Apple Watch SE 3 40mm
Apple Watch SE 3 40mm Starlight
Apple Magic Keyboard iPad White
Apple Pencil Pro
Apple PENCIL USB-C
Apple Adaptador 20w original
```

The source offers far more Apple products, but the store already sells most of them under a
different naming from another source, and a second entry for the same model is a defect on the
wall, not extra catalogue. Adding a model here is a deliberate act; it is never inferred from
what the source happens to list today.

**R12 — The list sits next to the classifier.** It lives in the same module so a test can prove
that every name in it resolves to a family; a non-Apple or misspelt name would otherwise be
skipped silently by the extraction. The Apple extract only consumes the list.

## 4. Selection

**R13 — A requested name is imported only when the source lists it.** Names are compared in the
normalised form (R8), so a difference in case, spacing or dashes does not lose a product, and a
source that repeats a name does not select it twice.

**R14 — Present keeps the order that was requested.** `present` holds the requested names the
source lists, in list order; `missing` holds the ones it does not.

**R15 — Missing is loud, not fatal.** Every requested name the source no longer lists is
printed. A rename upstream must not quietly remove a product from the store; the run still
finishes and still writes the products it did find.

**R16 — Nothing that was not requested is imported.** The source listing is read for the names
the list asks about; a row the list does not name never enters a seed file, whatever family the
classifier would have given it.

## 5. Slug

**R17 — An Apple slug is derived from the name.** Normalise (R8), drop one leading `apple `,
turn the remaining spaces into hyphens: `Apple Pencil USB-C` → `pencil-usb-c`,
`iPhone 18 Pro - 256 GB` → `iphone-18-pro-256-gb`. It is derived because the source's own
identifiers are not allowed into the repository.

**R18 — A phone slug comes from the source id.** The phone source has no separate slug: its
`id` is the slug, sometimes prefixed with `u-` for used units, so the prefix is stripped and the
rest is kebab-cased (NFD, diacritics and quotes dropped, non-alphanumeric runs to a hyphen, ends
trimmed): `u-iPhone 12 "Pro" Máx` → `iphone-12-pro-max`.

**R19 — A slug is an address the store owns, so it must be unique.** The Apple extract aborts
with `two products resolve to the same address: <slug>` when two requested products collide. The
phone extract keeps the first record it reads per slug and skips the rest.

## 6. Capacity

**R20 — A capacity is read from the name in one of two forms.** A range of two capacities, two
to four digits on each side, separated by a hyphen or an en dash with optional spaces, followed
by `GB` or `TB` (`256 - 512 GB`); or a single capacity, two to four digits followed by `GB` or
`TB` (`256GB`, `1 TB`).

**R21 — A range is two capacities and is never read twice.** When at least one range matches,
the single form is not consulted, because reading the range again as a lone number would
duplicate its upper end. The unit written after the range applies to both bounds:
`iPhone Duo 256 - 512 GB` → `256GB`, `512GB`.

**R22 — Capacities are normalised and de-duplicated.** The unit is uppercased and joined to the
number without a space (`256 GB` → `256GB`, `1 tb` → `1TB`); duplicates are removed keeping the
order they were first seen.

**R23 — A power rating is never a capacity.** A match must carry `GB` or `TB`, so `20w` in
"Apple Adaptador 20w original" is not a capacity and that product is sold without one. The
variant selector is built from this list, which is why the distinction matters.

**R24 — The phone source collapses colours into capacities.** Its variants carry colours the
destination cannot store, so they become one row per distinct capacity. Capacities that differ
only in spelling are one row (`1 TB`, `1TB` and `1 tb` are the same), the first-seen spelling
survives, order is preserved, blank capacities are ignored, and the record's `storages` list is
appended after the variant rows.

**R25 — No capacity means one variant with no storage.** A product the name gives no capacity
for is written with exactly one variant whose storage is `null`.

## 7. SKU

**R26 — A SKU is the slug, capacity-qualified when there is a capacity.** No storage gives the
slug alone (`pencil-pro`). With a storage, the slug is followed by the capacity lowercased with
every non-alphanumeric run removed: `iphone-18-pro-256-gb` + `256GB` →
`iphone-18-pro-256-gb-256gb`. Qualifying it is what keeps the same product sold by 256GB and
512GB from colliding on the unique SKU.

**R27 — The phone adapter applies the same shape.** Its `skuFor` strips non-alphanumerics
through the same key it uses to compare capacities, and a storage that strips to nothing yields
the bare slug.

## 8. The phone adapter

**R28 — One record becomes one product, or nothing.** Only phones belong: a record whose
category is `Sellados` or `Usados` is accepted regardless of its name, and a record whose name
starts with `iphone` is accepted regardless of its category. Everything else is dropped. The
family of every product this adapter writes is `IPHONE`.

**R29 — The condition rides on the name.** The destination has no field for it, so a record
whose category is `Usados` gets the suffix ` (usado)` appended to its display name, and the
suffix is never appended twice.

**R30 — The adapter carries no price and no stock.** They are sample data the seed generates;
the adapter's output shape has no field for them.

**R31 — Photography is served per family.** A reference is `/products/<family>`, the category
lowercased, then the file name. The family rides in the folder so the file name does not have to
repeat it, and a builder that forgets the family lands in the phone folder rather than at the
flat root, where no file lives any more. This module's source lists phones only, so every path
builder defaults to the phone family.

**R32 — The phone asset name is frozen.** `/products/<family>/iphone-<kebab name>.png`, and a name
that already starts with `iphone-` is not prefixed twice: `iPhone 15 "Pro" Máx` →
`/products/iphone/iphone-15-pro-max.png`. The comment calls the prefix the family's; the code uses
the constant `iphone`, which is the only family this source has (see D3).

**R33 — Candidates are tried in order, and only a real image counts.** The name as written comes
first (the condition suffix becomes part of the file name, `iphone-15-usado.png`), then the bare
model with a trailing parenthetical stripped (`iphone-15.png`), and no candidate is repeated.
The caller keeps the first candidate that is genuinely an image: the phone site answers `200`
with its app shell for any unknown path, so a missing asset looks like a success until the bytes
are checked for the PNG magic number.

**R34 — The downloaded file lands where the reference points.** `/products/<family>/<slug>-1.png`,
inside the same family folder as the reference, so a photograph can never land at the flat root.

## 9. Which photographs survive a re-run

**R35 — A rewrite must not delete the owner's photographs.** An extract rewrites the whole seed
file from what it just downloaded, and photographs added by hand live in the same `images`
array. A plain rewrite deletes that work while reporting success: nothing fails, and the store
quietly keeps only the photographs the script happened to fetch. The merge rule exists so that
cannot happen.

**R36 — The merge order is the run's reference first, then the file's.** The Apple extract reads
the existing seed file before writing (not on a dry run) and indexes its `images` by slug. For
each product: the reference the run produced takes the first slot, because it is the photograph
the source is authoritative for and it keeps an untouched product's gallery stable; then every
previous entry that is an owned product path and not already present, in the order the file had
them, which is the order the owner gave his own photographs. The number kept is printed.
Merging the result again changes nothing.

**R37 — Only an owned product path survives.** A reference is kept when it starts with
`/products/` and every segment after it is non-empty and neither `.` nor `..`. An absolute
address, an outside URL, a relative path and a reference that climbs out of the directory are
all dropped.

**R38 — Existence is not checked while merging.** A missing file is the seed's business, and it
already drops the reference rather than failing. Filtering on existence here would delete a
reference whenever the file was temporarily unreadable.

**R39 — The downloaded bytes are checked before they are stored as a photograph.** The Apple
extract requires `RIFF` at bytes 0-3 and `WEBP` at bytes 8-11; a landing page, an error page or
an HTML redirect would otherwise be written to disk as if it were a photograph. The phone
extract checks the PNG magic number for the same reason. The base extract names every download
`<slug>-<n>.webp` and does not inspect the bytes.

## 10. How the seed files merge

**R40 — The base file is required; the two extracts are optional.** `products.json` is read
unconditionally. `products-iphone.json` and `products-apple.json` are read only when the file
exists, so a clone that has not run those extracts seeds exactly what it did before them.

**R41 — The merge is a concatenation in a fixed order.** Base, then phones, then Apple. Every
product is upserted on `slug` and every variant on `sku`, so the seed is idempotent: running it
twice leaves the same rows, and rows are never deleted or recreated. A slug that appeared in two
files would be updated twice, the later file winning the product row, while variant rows the
earlier file created are never removed; today no slug and no SKU repeats across the three files
(90 products and 100 variants on disk).

**R42 — The split is always reported.** The seed prints one line naming how many products came
from each file and tagging the optional ones with ` (absent)`.

## 11. Featured products

**R43 — The pick is the alphabetically first slug of each family.** The products are sorted by
slug (`localeCompare`) and the first product of each category is featured. The comparison is by
slug, not by the order the files happen to have, so the pick is stable across runs and across
re-ordered files. The result is at most one product per family.

**R44 — The pick is derived from the two original files only.** Featured slugs are computed from
`products.json` and `products-iphone.json`, never from the concatenation that includes the Apple
extract: an extract adds catalogue to the store, it never moves a family's landing pick. An
empty set of products features nothing.

**R45 — The flag is written on create and on update.** The seed writes
`featured: featured.has(product.slug)` in the data used by both the create and the update path,
so a database seeded before this rule converges on the next run instead of keeping a stale flag.
Manual curation of the column is not supported: the next seed reverts it. The seed also prints
the featured slugs it wrote.

## 12. Image references resolve, or fall back to the placeholder

**R46 — Every reference is local and owned.** The base extract writes
`/products/<family>/<slug>-<n>.webp`, numbered from 1, family folder included, so a downloaded
photograph can never land at the flat root. The Apple extract writes `<family folder>/<slug>-1.webp`
and the phone extract writes `<family folder>/<slug>-1.png`, as described in R34.

**R47 — The base extract keeps the widest rendition the page advertises.** The CDN only serves
renditions it has already generated: requesting another width returns `403`. So the extract does
not guess a size; it keeps the widest rendition the page actually advertises for each asset.

**R48 — The base extract caps a gallery and prunes shared site furniture.** At most five images
per product. An asset used by more than five distinct products is treated as site furniture and
dropped; when every image of a product would be dropped, its first image is kept as the
fallback, and a product therefore never loses every image.

**R49 — The seed keeps only references that resolve on this machine.** Images are local-only and
never committed. `resolveImages` keeps an entry only when it starts with `/products/`, carries no
`..`, and the file exists under `public/` right now, so the database never advertises an image
the running app cannot serve. The number kept and the number dropped are reported.

**R50 — What does not resolve becomes the placeholder.** A clone has the references but not the
files, so its products end up with no reference at all. The UI then renders `/placeholder.webp`
from the single `PLACEHOLDER_IMAGE` constant: the product card shows a decorative placeholder
with the line "Imagen no disponible" and keeps its place on the wall; the product page does the
same in its gallery. Nothing is broken and no layout depends on the file existing.

## Known drift

These are places where a comment or spec statement does not describe what the code does. They are
recorded instead of quietly documented as if they were true. None of them is changed by this
document.

**D1 — Only the Apple extract preserves photographs.**
`src/features/catalog/seed/image-preservation.ts:9-10` says the rule "has to hold in all three
extraction runs", but `preserveLocalPhotographs` has exactly one caller,
`scripts/extract-apple-catalogue.ts:247`. `scripts/extract-iphone-catalog.ts:272-306` and
`scripts/extract-catalog.ts:393-410` build `images` only from what they downloaded and then
rewrite the whole file, so a photograph added by hand to a phone product or to a
`products.json` product is deleted by the next run of that extract.

**D2 — `(usado)` stays in the name, not in the slug.**
`src/features/catalog/seed/source-mapping.ts:178-179` says the condition suffix "stays in the name and
the slug". It stays in the name only: `mapSourceProduct` derives the slug from the id
(`slugFromId`, 96-98 and 210) and the display name from `displayName` (215), and the test pins
`slug: "iphone-13"` next to `name: "iPhone 13 (usado)"`
(`src/features/catalog/seed/source-mapping.test.ts:212-215`). The consequence is real: a `Usados`
record and a `Sellados` record of the same model resolve to the same slug, and
`scripts/extract-iphone-catalog.ts:244-246` keeps whichever one the API returned first and skips
the other.

**D3 — The asset prefix is `iphone`, not the family.**
`src/features/catalog/seed/source-mapping.ts:162-164` describes "the family prefix plus the
kebab-cased name". The prefix is the constant `ASSET_PREFIX = "iphone"` (55) and is used
regardless of the `family` passed in (168-170), so a name in another family would be looked up as
`/products/<family>/iphone-<name>.png`. Nothing visible breaks today because this module's source
lists phones only (R31), but the rule the comment states is not the rule the code implements.

**D4 — `(absent)` is keyed on emptiness, not on absence.**
`src/features/catalog/seed/catalog.ts:59-60` says each extract is "skipped silently when absent,
but the split is always reported". The report tags a file ` (absent)` when it contributed zero
products (`73` and `75`), so a seed file that exists but is empty is also reported as absent.

**D5 — The seed's product and variant count is stale.**
`prisma/seed.ts:33-35` states that running the seed twice "leaves 89 products and 98 variants".
The three seed files on disk today hold 90 products and 100 variants (`products.json` 64/68,
`products-iphone.json` 17/22, `products-apple.json` 9/10) with no repeated slug or SKU. The
idempotency claim is right; only the two numbers are out of date.

**D6 — `featured` is written on update, and the spec still says it is not.**
`prisma/seed.ts:136-141` documents that the flag is written "on the update path as well as on
create" and that manual curation is reverted; the code does exactly that (`130-149`).
`odd/tasks/public-catalog-mvp.md` S15 and log entry L33 still say the seed sets the flag "only on
create and never on update, which keeps manual changes alive across re-seeds". The drift is in the
spec text, not in the code: a manual change to the column does not survive the next seed.

**D7 — The two `skuFor` rules disagree on a blank capacity.**
`src/features/catalog/seed/apple-catalogue.ts:152-158` has no guard for a storage that strips to
nothing and would return `<slug>-` with a trailing hyphen, while
`src/features/catalog/seed/source-mapping.ts:153-159` returns the bare slug for the same input. This is
a divergence between the two implementations of one rule rather than a wrong comment, and it is
unreachable today because `storagesFromName` cannot produce a blank capacity.

**D8 — The pruned first image is a fallback, not an exemption.**
`scripts/extract-catalog.ts:309-313` says "Gallery slots beyond the first one are mostly site
furniture … A product never loses every image: its first image (the og:image) stays as a
fallback." The code applies the sharing budget to every image of the group, the first one
included, and restores `slice(0, 1)` only when the filtered list is empty
(`316-333`). A first image used by more than five distinct products is therefore dropped whenever
any later image survives the budget; it is kept only when nothing survives.
